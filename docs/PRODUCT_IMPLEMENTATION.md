## Следующий этап: продолжение работы и версии материалов

Реализовано поверх существующих экранов и DTO:

- После SOLO onboarding — личное развитие, отдельно поиск и профиль; у EXISTING_PARTNER сохраняется возврат к приглашению. Главная, «Сегодня» и профиль пары ведут к сохранённым занятиям, программам и доступным действиям знакомства.
- Конкретный run открывается по `/development?run=...`, программа — по `?program=...#programs`. Несохранённые ответы/заметки не записываются в браузерное хранилище. Статусы совместного результата объясняют ожидание второго и завершение.
- Явное обновление и ограниченное обновление при возвращении к странице перечитывают текущие серверные данные. Общая запись использует прежний контроль revision; конфликт требует сверки актуальной записи. WebSocket и отдельный движок рекомендаций не добавлены.
- Архив опубликованных материалов закрепляет вопросы и шкалы за `contentRevision`. Новые runs берут latest, прежние завершаются по своей редакции; реально отсутствующая публикация даёт `CONTENT_VERSION_UNAVAILABLE`. Доступ остаётся приоритетным, повтор не переписывает результат и не дублирует награду.
- [Воспроизводимая приёмка двух пользователей](TWO_USER_ACCEPTANCE.md) объединяет шесть изолированных локальных suite, два дополнительных набора экономики/событий и отдельный ручной порядок проверки Discord.

Изменений модели авторизации, схемы DB, зависимостей, production deploy/push или очистки целевой базы в этом этапе нет. Контракт development уточнён совместимо: форма DTO прежняя, добавлена явная ошибка отсутствующей версии и отдельная выборка незавершённых runs.

Текущая DB-проверка этого этапа: aggregate из шести наборов прошёл на шести новых `_test` базах локального replica set `vmesteContinuation`; отдельные economy и pair-event-settings прошли на новом локальном экземпляре с их прежним строгим guard. Проверены настоящие entry/onboarding, взаимное согласие, API partial/final, версия 1 → версия 2, однократные награды, конфликт/повтор правки, отзыв доступа и отсутствие чужих личных ответов. Guard aggregate отклоняет отсутствующий URI и внешний хост до соединения. Оба временных MongoDB-сервера остановлены; пользовательская база не использовалась.

Проверки кода этого этапа: полный `npm run lint`, `npx tsc --noEmit --incremental false`, `npm run build` и все 47 наборов `npm run check:self` пройдены. Новый `selfcheck:continuation-ui` проверяет реальные hooks через React adapter, гонки ответов, возврат к run/программе, статусы и ограничения refresh. Полный `check:agents` — 0 errors / 0 warnings после исправления распознавания существующего economy guard; allowlist не расширялся. `git diff --check` и проверка 54 относительных ссылок изменённых документов пройдены.

Окружение Discord проверено заново: `.env` и соответствующие переменные процесса отсутствуют, доступен только браузер без Discord-вкладок. Адрес Activity и две независимые сессии запрошены, но недоступны в текущей проверке. Реальные OAuth, iframe, два браузерных участника и offline/reload внутри Discord **не проверены**. Актуальный порядок — в [приёмке](TWO_USER_ACCEPTANCE.md); исторические результаты ниже не засчитываются повторно.

Попытка локального browser smoke готовой production-сборки через `npm run start -- --hostname 127.0.0.1 --port 3105` остановлена существующей instrumentation-проверкой: не заданы `DISCORD_CLIENT_SECRET`, `JWT_SECRET`, `MONGODB_URI`, `NEXT_PUBLIC_DISCORD_CLIENT_ID`. Подстановка фиктивного окружения и обход авторизации не выполнялись. Сервер остановлен; на 3105, 27018 и 27029 нет слушателей. Успешный build не обозначается как успешный runtime/browser smoke.

## Доказательства проверки предыдущего этапа

Выполнены lint, TypeScript без incremental, production build и все 46 наборов `check:self`, включая entry-pairing, matching-product, economy, product-workspace. Проверка архитектурных правил: 0 errors, 0 warnings; новых allowlist entries нет. Индексы новых моделей включены в release preflight.

На отдельной локальной MongoDB 8.0.28 в режиме replica set выполнены восемь наборов:

1. `integration:entry-onboarding` — минимальная OAuth-запись → сведения → 12 вопросов → Factor materialization → ровно 1 onboarding coin.
2. `integration:two-user-mvp` — конкурентные подтверждения → 1 Pair / 2 claims, три weekly/activity цикла, уведомления и закрытость ответов.
3. `integration:pair-lifecycle-remaining` — пауза/возобновление/завершение и оставшиеся lifecycle сценарии.
4. `integration:matching-social-flow` — карточка/реакции/единственное принятие, независимый reveal/отзыв/новый раунд, API guards и replay после блокировки.
5. `integration:matching-pair-transition` — гонка за последнее место, paused в лимите, rollback, освобождение места, отзыв/expiry и гонка Pair confirmation.
6. `integration:economy` — конкурентные награды, покупка/капсула, однократный перенос предмета в коллекцию, rollback, чужой доступ, завершение пары, баланс ledger.
7. `integration:product-workspace` — owner/private данные, partial/final пары, receipt-only idempotency, uppercase/lowercase одного Pair, конфликт версий, даты, старый content revision и lifecycle.
8. `integration:pair-event-settings` — настоящая дата отношений, календарные настройки, неизменность принятой истории, гонки refresh/config и accept/config, актуальный доступ до replay. Только несвязанный weekly evaluator заменён фиксированной `NOT_READY` projection; модели, guards и транзакции настоящие. [Подробности](PAIR_EVENT_SETTINGS_UPDATE.md).

Дополнительно независимый review и Mongo stress: 40 одновременных первых запусков и 12 одновременных завершений без первоначального кошелька. Исправлены найденные расщепление Pair id по регистру, сохранение содержимого общего пространства в idempotency cache, обход guards при cached replay и stale UI после запрета доступа.

Тестовая MongoDB подготовлена из [официального Windows ZIP](https://www.mongodb.com/docs/v8.0/tutorial/install-mongodb-on-windows-zip/), SHA-256 архива проверена. Все DB-наборы использовали отдельные `_test` базы, loopback-адрес и очистку только собственных синтетических записей. Пользовательская Atlas-база не читалась и не очищалась.

Локальный браузерный smoke на отдельных синтетических аккаунтах: первый вход → onboarding; библиотека → личная практика → сохранённый результат; кошелёк 1 → 4 монеты → покупка дополнительной анкеты → остаток 1; общая задача → назначение себе/20 минут → завершение → 0 минут незавершённой нагрузки. Четыре новых экрана просмотрены визуально в существующем стиле. Найденная ложная сетевая ошибка после отмены старого запроса исправлена в общем клиенте; regression воспроизводит сбой на старом коде, повторное открытие пространства проходит без ошибки. Для этой проверки временный loopback wrapper подставлял настоящую тестовую session JWT только для собственных fixtures; production auth-код не менялся. Реальный OAuth, Discord iframe, физический телефон и два параллельных браузера этим smoke не проверялись.

## Предыдущий порядок проверки владельцем

Сначала нужны рабочие переменные существующего Discord/DB окружения и адрес Activity. В локальной копии они не обнаружены; секреты не следует передавать в переписке. На целевой базе выполняется существующий release preflight; добавочные индексы применяются явно после его отчёта. Автоматического production deploy или DB reset не было.

В Discord проверить двумя аккаунтами:

1. Новый одиночка проходит вход и onboarding, получает одну монету; повтор открытия не начисляет ещё одну.
2. Существующая пара связывается по коду/ссылке: второй соглашается, первый сверяет имя/код и подтверждает; до обоих Pair нет.
3. Для двух одиночек — публикация карточки, девять реакций и три ответа, ответ получателя, независимая тема и предложение пары.
4. Оба проходят совместную практику: после первого частично, после второго общий итог и награды. Чужие личные заметки не видны.
5. В общей жизни — задача, резерв желания, цель с этапами, две валюты бюджета, годовщина и повторение; одновременное редактирование предлагает обновление.
6. В магазине — покупка, повтор запроса, дополнительный материал, капсула с шансами и перенос коллекционного предмета в «Наше».

## Согласованное продолжение

Telegram/mobile авторизация, научно проверенные пакеты и админка, аналитика повторяющихся конфликтов/цикла, новое сопровождение расставания/архив, родительство и recovery удаления аккаунта отложены владельцем. Уведомления вне приложения, загрузка/хостинг фото, карта воспоминаний и внешнее бронирование сейчас не реализованы. Локальные проверки не заменяют Discord iframe smoke, Atlas release проверку и содержательную оценку демонстрационных материалов.

Отдельная следующая задача — редактирование политик использования уже собранных ответов. До реализации владелец должен определить: что отзывает согласие (будущие вычисления, текущие grants и/или сохранённые производные данные); как обрабатываются уже раскрытые партнёру ответы, снимки и экспорт; нужны ли новые раунды вместо изменения прошлого согласия; какие подтверждения и тексты предупреждений обязательны. Этот этап не меняет действующие capture policies задним числом и не обещает отозвать уже увиденные данные.
