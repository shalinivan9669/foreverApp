# Локальная приёмка без Discord

`acceptance:local` воспроизводит шесть существующих интеграционных наборов на новом локальном MongoDB replica set. `acceptance:browser` запускает текущую production-сборку Next.js и два синтетических аккаунта для ручной проверки интерфейса. Эти команды не подтверждают реальный Discord OAuth, SDK, iframe и настройки внешнего приложения.

## Запуск

Нужны установленные зависимости проекта, Node.js и уже установленный `mongod`. Команды не скачивают MongoDB и не устанавливают зависимости. Путь к исполняемому файлу задаётся явно:

```powershell
npm run acceptance:local -- --mongod 'C:\path\to\mongod.exe'
```

Альтернативно можно задать `LOCAL_ACCEPTANCE_MONGOD` только для локальной команды. Это настройка инструмента, не новая production-переменная приложения. Значения `MONGODB_URI`, `MATCHING_TEST_MONGODB_URI`, JWT и Discord-секреты из текущего окружения не используются: дочерние процессы получают разрешённый минимум системных переменных и сгенерированные синтетические настройки.

Перед запуском проверяется отсутствие `.env`, `.env.local`, `.env.production`, `.env.production.local` в корне проекта. При наличии любого из них команда отказывается продолжать, не читая и не изменяя файл: production Next автоматически загружает такие файлы. Для проверки используйте отдельную рабочую копию без реальных настроек; не удаляйте файлы рабочего приложения ради теста.

По умолчанию MongoDB занимает `127.0.0.1:27039`, приложение участника А — порт `3106`, приложение участника Б — `3108`, локальная выдача тестовых сессий — `3107`. Опции `--mongo-port`, `--app-port`, `--partner-app-port`, `--login-port` меняют только номера портов; все четыре номера должны различаться и быть в диапазоне 1024–65535. Занятые порты вызывают отказ, существующие процессы команда не останавливает.

## Шесть серверных наборов

`acceptance:local` последовательно запускает `entry-onboarding`, `matching-social-flow`, `matching-pair-transition`, `two-user-mvp`, `pair-lifecycle-remaining`, `product-workspace` через существующий `two-user-acceptance.integration.ts`. Каждый набор получает новую базу с суффиксом `_test`. В выводе остаются только имя набора, этап и результат; ответы, заметки, токены и внутренние идентификаторы не печатаются. Агрегат ограничен пятью минутами: при зависании возвращается `LOCAL_ACCEPTANCE_INTEGRATION_TIMEOUT` и выполняется очистка собственного дерева процессов. Экономика и настройки событий пары с отдельным строгим URI guard в этот агрегат не входят.

Независимая быстрая проверка границ инструмента:

```powershell
npm run selfcheck:local-acceptance
```

Она проверяет аргументы, отсутствие унаследованных секретов, допустимую область очистки и жёсткое связывание двух локальных адресов с двумя участниками. Эта проверка не запускает процессы и не обращается к БД.

## Два участника в браузере

Сначала соберите текущую рабочую копию, затем запустите режим браузера:

```powershell
npm run build
npm run acceptance:browser -- --mongod 'C:\path\to\mongod.exe'
```

После строки `browser-ready` откройте выведенные ссылки. При стандартных портах:

- Участник А: `http://vmeste-a.localhost:3107/a`.
- Участник Б: `http://vmeste-b.localhost:3107/b`.

Обе ссылки перенаправляют на `/main-menu` настоящего Next-сервера своего участника: А использует `vmeste-a.localhost:3106`, Б — `vmeste-b.localhost:3108`. Разные имена хоста разделяют cookie даже в одном профиле браузера. Используйте браузер, в котором поддомены `.localhost` разрешаются в loopback (проверено в Chromium). Передаваемую другому участнику ссылку приглашения открывайте с его хостом **и портом**, сохраняя путь и query string: в production оба используют общий адрес, а локальная смена origin нужна только для разделения cookie.

Установленная версия Next строит абсолютный URL запроса с настроенным `hostname` сервера. Поэтому для двух разных origin инструмент запускает два отдельных дочерних процесса через документированный custom-server API `next({ dev: false, hostname, port })`. Оба используют одну текущую production-сборку и одну новую тестовую БД; каждый TCP-сервер привязан только к `127.0.0.1` и принимает ровно свой `Host`. `Origin`, cookie, production guards и настройки Next не переписываются. Один обычный `next start --hostname 127.0.0.1` для двух browser origins не подходит: его URL не совпадает с исходным `Origin` мутации.

Создаются два совершеннолетних участника `EXISTING_PARTNER` с полностью пройденным onboarding через существующие доменные сервисы; пары ещё нет. Ответы синтетические, необязательные вопросы пропущены. У участника А также есть 35 незавершённых личных занятий из реальной опубликованной редакции v1 с разными прошлыми неделями: можно проверить «Показать ещё» и открыть старое прохождение. Они не содержат ответов или результатов и не дают наград за создание.

В browser-режиме `--scenario` выбирает начальное состояние. Допустимы `existing-partner` (по умолчанию), `solo`, `onboarding`, `first-entry`, `matching`, `matching-connection`, `notifications`. `solo` создаёт личный режим без пары; `onboarding` оставляет начальную анкету незаполненной и открывает `/mvp-onboarding`; `matching` публикует синтетические карточки для проверки composer; `matching-connection` создаёт знакомство с темами до и после взаимного раскрытия через штатные доменные сервисы. Все варианты предназначены только для новой локальной тестовой БД и не меняют production-вход.

`first-entry` создаёт только синтетическую идентичность и действующую подписанную сессию. Ни cohort/entry, ни onboarding, ни карточка или личные занятия не подготовлены. Открывается `/entry`; выбор цели, подтверждения, 12 вопросов, карточка, обязательные предпочтения, разрешения на подбор и публикация выполняются через UI. Этот fixture проверяет продуктовый первый вход после bootstrap, но не настоящий Discord OAuth.

`notifications` создаёт активную пару с текущим циклом и реальной частично завершённой активностью: участник А уже отправил отзыв, Б ещё должен ответить. Более 205 новых записей оставляют старую целевую активность за лимитом истории; другая текущая активность содержит сохранённый отзыв А без финального resultSummary для проверки отдельного завершения после прерывания. Есть уведомления текущего цикла, прежней завершённой пары и отсутствующей активности. Перед браузерной приёмкой fixture проверяет адресное чтение, собственный флаг отправки, чужую пару, private-доступ и отсутствие ответов в DTO через реальные маршруты. Начальные состояния готовятся исключительно на собственной тестовой БД.

Для параллельных browser-запусков одного профиля нужны разные порты **и имена хостов**: cookie не разделяются по порту. Опция `--host-prefix` принимает только `vmeste` (по умолчанию), `vmeste-workspace` или `vmeste-matching`; например, последний вариант использует `vmeste-matching-a.localhost` и `vmeste-matching-b.localhost`. Произвольные хосты не разрешены. Проверки `Host`, `Origin`, bootstrap и probe используют одну выбранную пару имён.

```powershell
npm run acceptance:browser -- --mongod 'C:\path\to\mongod.exe' --scenario matching --host-prefix vmeste-matching --mongo-port 27041 --app-port 3126 --partner-app-port 3128 --login-port 3127
```

Рекомендуемый маршрут: увидеть все 35 занятий А → открыть старое занятие → создать приглашение → открыть его участником Б → подтвердить с обеих сторон → совместное занятие с первым/вторым завершением → одновременное изменение общей записи и разрешение конфликта → перезагрузка и возврат. Подробные ожидания находятся в [приёмке двумя пользователями](TWO_USER_ACCEPTANCE.md).

Отдельный локальный HTTP-сервер выдаёт только настоящие подписанные cookie-сессии для этих двух фиксированных субъектов с `SessionSubject`. Он не добавляет маршрутов в приложение, не принимает произвольный `userId`, не меняет production guards и не имитирует OAuth. Cookie в тестовом HTTP-окружении имеет `HttpOnly`, `SameSite=Lax`, срок два часа; это не изменение cookie-политики реального входа. Токены отсутствуют в URL, JSON, файлах и консольном выводе. `GET /status` локального сервера возвращает только готовность, число участников и тип fixture.

## Остановка и очистка

Для отдельного аудита аналитической цепочки используйте integration mode с `--suite factors`: `npm run acceptance:local -- --mongod 'C:\path\to\mongod.exe' --suite factors`. Запускаются три целевых набора вместо шести продуктовых. Это characterization-аудит: он подтверждает работающий движок и явно зафиксированные отсутствующие продуктовые связи; PASS не означает готовность сквозного анкетного расчёта. Подробности: [FACTOR_PROFILE_AUDIT.md](FACTOR_PROFILE_AUDIT.md).

В терминале нажмите Enter или Ctrl+C. Для управляемого завершения доступен также `POST http://127.0.0.1:3107/stop` с точным заголовком `Origin: http://127.0.0.1:3107`; этот маршрут существует только у отдельного локального инструмента. Режим браузера работает до явной остановки либо ошибки принадлежащего ему процесса.

После остановки приёма запросов bootstrap явно закрывает принадлежащие ему keep-alive соединения, чтобы браузерный сокет не удерживал завершение и последующую очистку. Штатный результат содержит событие `cleaned-up` и код завершения 0; отсутствие listener само по себе не доказывает удаление временного каталога.

Инструмент создаёт новый каталог `vmeste-local-acceptance-*` через `mkdtemp` и запускает свой `mongod`, привязанный к IPv4 loopback. Перед инициализацией replica set он проверяет полученный `getCmdLineOpts`: путь данных, порт и имя replica set должны совпасть с принадлежащим запуску процессом. Существующий локальный или внешний MongoDB не является допустимой целью. Остановка MongoDB использует сохранённый дескриптор собственного дочернего процесса; команда `shutdown` по URI не отправляется, чтобы автоматическое переподключение клиента не затронуло другой сервер.

В `finally` закрываются локальный HTTP-сервер и собственные процессы; под Windows при прерывании завершается только дерево запущенного процесса, чтобы активный интеграционный набор не остался сиротой. Синтетические browser User/SessionSubject/runs удаляются адресно. Затем собственный MongoDB останавливается, и только после подтверждения завершения всех процессов удаляется ровно созданный этим запуском временный каталог вместе с остальными синтетическими данными. `dropDatabase`, массовый сброс общей базы, поиск/удаление старых каталогов и остановка существующих серверов не применяются. Если процесс не завершился, очистка каталога запрещается и возвращается ошибка.

При принудительном завершении всей ОС или безусловном убийстве самого управляющего процесса JavaScript `finally` исполниться не может. Такой запуск нельзя считать штатно очищенным; команда не пытается автоматически удалять оставшиеся от прежних запусков каталоги.
