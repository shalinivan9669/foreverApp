# Формы входа и знакомства — UX/UI, 2026-09-07

Классификация: последовательные `FEATURE_CHANGE` этапов 7A–7D из [плана](UX_UI_IMPLEMENTATION_PLAN.md). HTTP-контракты, схемы БД, согласия, Factor NEW_ONLY и условия образования пары сохранены. Production-зависимости не добавлялись.

## Начальная настройка — 7A

`src/app/mvp-onboarding/page.tsx` показывает определения трёх способов использования ответа перед согласием. Юридические подтверждения видимы постоянно; только технические версии убраны в доступные подробности. У каждого ответа выбор policy остаётся пустым до явного действия. Есть текстовые причины недоступности продолжения, счётчик прогресса, фокус заголовка следующего вопроса и блокировка изменения/повторной отправки во время сохранения. Пропуск доступен только для optional-вопросов; обязательные вопросы не сокращены. Сохранённые ответы остаются на сервере, несохранённый ответ — только в памяти текущего экрана.

## Приглашение — 7B

`/invite` разделяет создание собственного приглашения и ввод кода партнёра. Этапы показываются по полученному серверному состоянию: приглашение → подтверждение получателя → подтверждение владельца. ACTIVE с claim не называется созданной парой. Имя, постоянный код и отдельная добровольная отметка сверки сохранены у обеих сторон. `/join` показывает те же этапы относительно получателя. Во время подтверждённого ожидания доступны личные занятия. Отмена и перевыпуск используют общий доступный Dialog; ошибки сохраняют возможность повторить действие.

## Независимые ответы — 7C

`MatchingConnectionPage` для каждой темы показывает две карточки готовности; peer text рендерится только при `revealed && partnerAnswer`. После первого ответа экран явно сообщает об ожидании без призыва отвечать снова. Разрешённое сравнение адаптируется от одной колонки к двум. Правила раскрытия/отзыва/нового раунда находятся в доступных подробностях; согласие перед собственной отправкой остаётся рядом с формой. Новый раунд после раскрытия начинается сознательным открытием формы.

Ключ темы связан с connection/topic, а не с ответом или revealed-флагом. Обновление состояния не перемонтирует редактор и не стирает черновик. Успех явно очищает черновик и согласие; ошибка сохраняет их. Повтор отправки неизменённой команды использует тот же Idempotency-Key. Локальная блокировка исключает параллельную mutation; поколения запросов не позволяют устаревшей загрузке заменить результат mutation. Состояние можно обновить вручную и при возвращении в видимую вкладку с прежним cooldown. Подтверждённая потеря доступа убирает темы без exit-анимации.

Локальная браузерная проверка воспроизвела потерю фокуса после первого ответа: выбор следующей темы закрывал текущий `<details>`, поэтому внутренний заголовок уже нельзя было сфокусировать. Исправлено: после подтверждённого сохранения фокус возвращается на всегда видимый `<summary>` с текущим статусом. Сознательное открытие формы нового раунда переводит фокус в textarea после её появления. Эти переходы проверяются повторением сценария в браузере; статический SSR/selfcheck не выдаётся за доказательство DOM focus.

## Карточка и ответ — 7D

Карточка кандидата использует общий Dialog: фон заблокирован, содержание прокручивается одним контейнером. Видны ожидания, вклад и границы с обозначенными dealbreakers. Прочтение карточки не открывает заполнение автоматически: кнопка «Начать ответ» запускает реакции → все вопросы → проверку. Каждый пункт требует отдельной реакции; обычное несогласие разрешено, AGAINST для явно непреодолимой границы блокирует отправку. Сохранена совместимость с существующими карточками на два вопроса.

Первоначальное чтение карточки можно закрыть даже при медленном запросе: его AbortController отменяется, поздний результат или ошибка не открывают карточку и не оставляют ошибку отменённого чтения на ленте. Отправка интереса имеет отдельный `mutationLoading`; закрытие и смена кандидата блокируются до её результата независимо от наличия `candidateCard`. Подтверждённая потеря доступа имеет приоритет и немедленно скрывает приватный узел.

Реакции, ответы и три добровольных подтверждения сохраняются между шагами в памяти. Проверка показывает весь отправляемый текст; поле не имеет ключа из введённого значения. Первый интерес/ответ раскрывается адресату сразу после отправки, о чём сказано отдельно от независимых раундов. Отправка и повтор используют один ключ для неизменённого содержимого, переданный через необязательный параметр клиентского API; wire body не меняется. Редактирование создаёт новую попытку. Новая карточка/закрытие инвалидируют предыдущую загрузку, отказ в доступе очищает отображение.

После подтверждения блокировки прежний Like немедленно удаляется из клиентского состояния, ещё до повторного guarded GET; задержка или сетевая ошибка этого GET не сохраняет прежние тексты и действия. Отказ 403/404/MATCHING_BLOCKED при открытии кандидата или отправке интереса удаляет его также из лежащей под диалогом ленты. При 401 очищается вся лента и курсор. Одновременно отменяется/инвалидируется прежний запрос ленты, поэтому поздний ответ не возвращает удалённые карточки.

## Предупреждение об уходе

`useUnsavedChanges` объединяет активные черновики, предупреждает нативным подтверждением перед ссылками/программным BackBar/закрытием сценария и блокирует уход во время отправки. `beforeunload` защищает перезагрузку/закрытие, насколько это разрешено браузером. В Chromium поддерживающий Navigation API перехватывается также browser Back/Forward; хосты без этого API имеют защиту ссылок, кнопки «Назад» приложения и полной выгрузки. Приватный текст не записывается в localStorage/sessionStorage/URL. Хранилища browser history не подменяются.

- `check:agents:changed`: 0 ошибок и предупреждений; allowlist не менялся.
- `selfcheck:matching-request-race` исполняет настоящие hooks через React adapter: смена ресурса во время mutation, scoped loading/error/locks, старый отказ/ответ, немедленная очистка после block ACK до завершения повторного GET, сетевая ошибка после block, 401/403/404/block в detail и createLike, поздний feed GET после отказа. Полные приватные payloads в вывод не попадают.
- Для браузерной матрицы добавлен только локальный `scripts/lib/local-acceptance-matching.ts`: реальные services готовят синтетические matching/matching-connection состояния в БД, привязанной к runId и loopback replica set. Fixture не создаёт production endpoint и не обходит OAuth. Во втором сценарии одна тема ожидает Б, другая уже раскрыта; остальные пусты. Дальнейшие переходы проверяются обычными действиями интерфейса.

Браузерные результаты общего запуска и итоговый build фиксируются в общей документации приёмки корневой задачи. Статические проверки сами по себе не удостоверяют keyboard/focus/iframe/Discord. Реальная среда Discord и синтетический локальный браузер различаются.
