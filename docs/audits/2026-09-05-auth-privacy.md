## Подтверждённые расхождения и ограничения

1. **Дефект текста:** [onboarding page:60](../../src/app/mvp-onboarding/page.tsx) обещает 10 вопросов; `MVP_ONBOARDING_QUESTIONS` содержит 12. Текущий UI последовательно проходит весь массив, допуская skip трёх optional. Серверный `canCompleteMvpOnboarding` требует только 9 обязательных: формулировка «обязательно ответить на все 12» тоже неверна.
2. **Дефект обещания:** [onboarding page:512](../../src/app/mvp-onboarding/page.tsx) обещает пересмотр privacy в настройках; [saveAnswer:652](../../src/domain/services/mvpOnboarding.service.ts) отклоняет completed, а start не переоткрывает. Решение о новой edit/revoke семантике открыто; безопасная ближайшая правка — привести текст к факту.
3. **Незавершённый fresh-user маршрут:** identity upsert записывает username/avatar/id без personal/location. Onboarding не пишет User (сам selfcheck запрещает такой импорт), profile overview/details доступны для чтения, а MatchingCardForm не собирает собственную демографию. Discovery ожидает её. Backend profile writer существует, следовательно дело не в названии поля или отсутствии всей подсистемы. Дополнительно `projectDiscovery:801` обращается к `user.personal.age` без проверки существования personal; для действительно partial document возможен INTERNAL вместо объяснимого readiness failure. Этот конкретный ответ API не воспроизводился.
4. **Статически выявленный пробел восстановления удаления после ошибки:** [accountDeletion.service.ts:532](../../src/domain/services/accountDeletion.service.ts) вызывает beginDeletion; [accountWriteBarrier.service.ts:248](../../src/domain/services/accountWriteBarrier.service.ts) оставляет `accountState=DELETING`. После ошибки [accountDeletion.service.ts:577](../../src/domain/services/accountDeletion.service.ts) меняет PrivacyRequest на FAILED, не возвращает ACTIVE. [GET deletion-request:24](../../src/app/api/privacy/deletion-request/route.ts) использует обычный requireSession; тот идёт через active-only `acquireAuthenticated`. [settings page:11](../../src/app/profile/(tabs)/settings/page.tsx) сначала требует useCurrentUser и при его отсутствии не рендерит PrivacySettingsHub. Поэтому после reload стандартный UI не может получить состояние FAILED/продолжить удаление, хотя [execute route:14](../../src/app/api/privacy/deletion-request/execute/route.ts) специально разрешает deletion-control в DELETING. В оставшейся открытой странице повтор execute возможен. Это проверенная цепь кода; failure injection/браузерный сценарий не запускался.
5. **Несоответствие описания восстановления:** `toOwnerDeletionRequestDTO:73` помечает любой не-EXECUTED как accountAndSessions=UNCHANGED; UI FAILED говорит, что сессии не считаются удалёнными. После beginDeletion обычные сессии уже заблокированы, а endPair выполняется до основной cleanup transaction. Поэтому ошибка не всегда означает неизменённые аккаунт/связь/доступ. Возможная задача recovery+copy с проверкой стадий сбоя зарегистрирована, но отложена владельцем после аудита.
6. **Дрейф активной документации:** SECURITY и TARGET_DOMAIN_OPERATIONS говорят о rotation «при подтверждении»/до destructive work. Реальный ранний барьер — DELETING без rotation, с сохранением deletion-control retry; rotation выполняется в markDeleted. TARGET_DOMAIN_OPERATIONS §5 также говорит invitation-only, хотя Matching formation уже существует. Эти формулировки следует согласовать с кодом отдельно от изменения политики.
7. **Удаление не стирает всю совместную историю:** accountDeletion сохраняет/псевдонимизирует Pair, PairActivity, PairQuestionnaireSession, WeeklyCycle, PairStateSnapshot, PairFactorEvaluationSnapshot; удаляет owner answers и отдельные личные/Matching/Factor записи, сохраняет прежние уведомления другого участника вокруг endPair. «Удаляется весь граф пары» неверно. Полнота удаления ссылок и требования архивов/backup требуют DB fixtures и принятой политики D04/D12; здесь это не правовое заключение.

## Зависимости, важные перед изменением аналитики/Matching

```text
Discord identity → User (может быть partial)
                   ├→ SessionSubject / account write barrier
                   ├→ MvpOnboardingSession (content/policy/answer revisions)
                   │    → onboardingFactorEngine → EvidenceEvent / IndividualFactorSnapshot
                   └→ personal/location → discovery projection + invalidation of active card/grants

capture mode + purpose + privacy class + consent revision
  → owner computation / separate matching grant / pair use
  → disclosure projection → UI, export, notifications

Pair context + membership + lifecycle fence
  → SafetyGate / PartnerSignal / pair summaries
  → end / export / account deletion and retained history
```

Не заменять capture-policy enum терминами источника без анализа purpose/projection consumers. Не считать изменение User.personal безобидной формой: оно выключает поиск и отзывает выдачи кандидатов. При privacy edits нужны новая consent/evidence revision, правила старых immutable snapshots и отзыв производных представлений. Удаление продолжает чистить legacy `vector_snapshots`/`evidence_events`; наличие этих cleanup ветвей не доказывает активный legacy analytics runtime.
