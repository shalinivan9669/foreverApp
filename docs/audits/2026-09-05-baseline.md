## Статусы и достоверность

**НАЙДЕНО** — прочитана реализация и её связь с потребителем. **ЧАСТИЧНО** — перечислена работающая по коду часть и конкретный пробел. **ПРОВЕРЕНО ЛОКАЛЬНО** — пройдена названная автоматическая проверка в этой рабочей копии. **НЕ ПРОВЕРЕНО** — нет соответствующего запуска/достаточного чтения. **НЕ НАЙДЕНО ПОСЛЕ ПОИСКА** — указан поиск и граница его охвата. Эти статусы не взаимозаменяемы: существующая state machine и зелёный тест чистой функции не подтверждают транзакцию или полный UI-сценарий.

## Карта зависимостей аналитики и Matching

```text
definitions/registry + source bindings + capture/consent policy
  → onboarding / questionnaires / weekly check-in / activity feedback
  → разрешённые source-bound immutable EvidenceEvent
  → OWNER_PROFILE / PAIR_MODEL IndividualFactorSnapshot / PairFactorSnapshot
      → owner profile DTO
      → PairFactorEvaluationSnapshot → safe Pair Summary
          → RecommendationDecision → PairActivity → feedback → new evidence

matching card actual answers
  → purpose=MATCHING Evidence → unpaired MATCHING IndividualFactorSnapshot
  + MatchingUseGrant + PartnerPreferenceProfile
  → actual profile + internal MatchingEvaluationSnapshot
  → coarse discovery / version-pinned feed / candidate grant
  → qualitative DTO → Like → MatchingConnection → two confirmations → Pair

PersonalDailyCheckIn → personal today + explicit PartnerSignal
  (mutable источник; его writer в Factor evidence не найден;
   сводка today отдельно поддерживает OWNER_PROFILE Factor fallback)

privacy/export/deletion + session/write barriers + pair lifecycle
  контролируют все соответствующие чтения, источники, snapshots и связи
```

Подробные writers/readers, символы, policy/version dependencies и legacy search приведены в [аналитической карте](2026-09-05-analytics-matching.md). При будущем изменении нельзя ограничиваться формулой: проверить published registry/hash, historical replay, purpose/consent, grants, preference/evaluation revision, feed invalidation, candidate disclosure, pair formation, экспорт/удаление и rollback. Реальный перенос данных и состояние legacy-коллекций не проверены. На основании текущего source tree нет причины повторно проектировать миграцию runtime с шести векторов: обнаруженный runtime уже NEW_ONLY.

## Одна рекомендуемая следующая задача

**Статус: ОТЛОЖЕНА ВЛАДЕЛЬЦЕМ после аудита.** Следующее описание фиксирует прежнее предложение и не разрешает начинать работу над удалением. Текущий приоритет и пакет вопросов: [PRODUCT_DECISIONS_PENDING.md](../PRODUCT_DECISIONS_PENDING.md).

**Воспроизвести и восстановить owner-only повтор удаления после сбоя и перезагрузки страницы.** Пользовательский результат: человек с уже подтверждённым, но не завершившимся удалением видит правдивый статус и может безопасно повторить удаление, не получая доступ к обычным функциям аккаунта в состоянии DELETING.

- Основание: G07, D12, AT-037/038/041/044. `accountDeletionService.execute` переводит request в FAILED после сбоя, но оставляет барьер DELETING. Специальный execute guard допускает повтор; GET статуса и bootstrap settings используют обычный guard и не открывают путь после cold reload. Существующий security selfcheck этого полного recovery пути не доказывает.
- Режим будущей задачи: `SECURITY_FIX`, риск средний. Сначала добавить сфокусированное воспроизведение в разрешённой изолированной среде/с подменёнными границами. Если гипотеза не воспроизводится, зафиксировать причину и не менять access policy по предположению.
- Область предполагаемого изменения после воспроизведения: privacy status route, узкий owner deletion-control projection/guard и bootstrap privacy UI; связанные client API/DTO — только если нужны для конечного пути. Общий запрет обычных запросов в DELETING, write leases и durable DELETED tombstone должны сохраниться. Ни миграции, ни reset, ни изменения экономики/cohort в задачу не входят.
- Приёмка: сбой после установки барьера до завершения cleanup → FAILED без ложного success/UNCHANGED; reload с сохранённой допустимой сессией → доступен только собственный минимальный статус/повтор; чужой actor, неверная/истёкшая session version и DELETED получают отказ; обычные API остаются закрыты; два retry не дублируют cleanup и не выдают ложный success; уже выполненный endPair отражается правдиво, поскольку он предшествует основной cleanup transaction; успешное удаление отзывает прежние сессии; ответы/секреты не попадают в DTO/логи.
- Проверки: targeted recovery test, security-critical и соответствующая isolated deletion integration, types, lint затронутых файлов, agent diagnostics. Изменение auth/access contract требует отдельного согласования согласно `AGENTS.md`; этот аудит подготовил конкретный сценарий, но не выполнял исправление.

Fresh-Matching baseline и cohort остаются существенным продуктовым препятствием G01/D17. Они записаны как решение для следующего планирования, а не подменены маленьким исправлением текста или молчаливым добавлением новых полей. Новых продуктовых решений в рамках аудита не принято.
