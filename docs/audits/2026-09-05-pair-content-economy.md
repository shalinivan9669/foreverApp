## Зависимости аналитики, которые нельзя оборвать миграцией

1. Weekly UI closed answers → `weeklyCheckInService` → `processWeeklyFactorCheckIn` → evidence/individual snapshots → weekly pair evaluations → `weeklyCycleService`/`PairStateSnapshot` → PairSummary/history/recommendation. Поля `closeness/fatigue/...` являются типизированными входами current state; сами по себе они не означают старый six-axis passport.
2. `ActivityTemplate.actionDefinition` + `targetFactorKeys` + registry version → eligibility/recommendation → `PairActivity` → role-specific task feedback (`activityFactorRuntime.service.ts:1660`, source `TASK_RESULT`) и pair completion (`:1771`, source `PAIR_ACTIVITY`) → individual/pair/evaluation snapshots → owner profile/следующая рекомендация. Это реальные downstream-потребители общего Factor слоя.
3. PairEvent читает только текущую качественную weekly-проекцию, lifecycle/calendar и bounded activity history (`pairEvent.service.ts:766`); его target factors/action versions должны оставаться совместимы при изменении registry. Он не является старым анализатором сырых weekly полей.
4. История выбирает сохранённый canonical snapshot, не пересчитывает старый результат из новых raw inputs (`pairHistory.service.ts:396`). Изменение определения сигнала требует совместимости исторического display, а не переписывания истории.
5. Сохранились `RelationshipActivity`/`relationshipActivityLegacyService`/legacy DTO, но их потребитель в active `src` не найден: actual activity GET использует `pairActivityReadService`. Это остаточный compatibility-код, не доказательство использования старой аналитики. Удаление не выполнялось.

## Единая следующая задача

Прежняя [рекомендация recovery удаления](2026-09-05-baseline.md#одна-рекомендуемая-следующая-задача) **отложена владельцем после аудита**. Текущий шаг — [пакет вопросов о полном продукте](../PRODUCT_DECISIONS_PENDING.md), ответы пока ожидаются. PairEvent integration и D01/D04/D08/D14/D15/D21/D25 остаются в реестре; полный набор и очередь модулей будут определены ответами, а не автоматически сокращены до одной малой задачи.

При финальной независимой перепроверке подтверждена цепочка G07: `accountDeletion.service.ts:532` успешно ставит DELETING; сбой после этого и до успешного завершения приводит к FAILED (`:572–582`), не снимая барьер. Обычные GET status и `/api/users/me` используют active-only guard; settings при холодной загрузке без `currentUser` не рендерит PrivacySettingsHub (`src/app/profile/(tabs)/settings/page.tsx:20`). Store инициализируется пустым и не использует persist (`useEntitiesStore.ts:63–73`). Execute имеет специальный deletion-control guard, допускающий DELETING с текущей валидной session version. Поэтому повтор из сохранённой открытой страницы или прямой допустимый запрос возможен, но обычный UI после холодной перезагрузки не восстанавливает этот путь. Ошибка до успешного beginDeletion или после успешного completion не доказывает именно этот сценарий. Проверка была статической, без БД, браузера или новых тестов; privacy/auth документы не редактировались.

Дополнительный корпус этой перепроверки: `privacy/deletion-request/route.ts`, `privacy/deletion-request/execute/route.ts`, `users/me/route.ts`, `lib/auth/guards.ts`, `sessionRevocation.service.ts`, `accountDeletion.service.ts` (стадии execute/cleanup), `accountWriteBarrier.service.ts` (active filter, lease, beginDeletion, wait, markDeleted), `privacyRequest.service.ts` (DTO/current), settings page, `PrivacySettingsHub.tsx` (load/execute/render), `useCurrentUser.ts`, `useEntitiesStore.ts`, `users.api.ts`; поиском проверены дополнительные импорты PrivacySettingsHub и persist/storage.
