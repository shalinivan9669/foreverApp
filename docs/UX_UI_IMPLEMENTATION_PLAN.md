## Цель и границы

Сделать первый и повторный вход понятнее: одно главное действие, доступные вторичные разделы, различимые состояния и последовательные формы. Сохранить тёплый стиль. Сначала исправить читаемость и композицию, затем оценивать необходимость анимации.

Сквозные ограничения: Factor NEW_ONLY, обязательные вопросы, согласия и capture policy, независимые ответы и раскрытие, двойное подтверждение пары, lifecycle, session/ownership, DTO, API, схемы БД, награды и бесплатное ядро остаются в действующем контракте. Личные функции доступны и после формирования пары. Приватные черновики остаются в памяти; новые способы хранения не входят в план. Gateway-бот, deployment, миграции и сбросы данных исключены.

## Карта предлагаемой общей навигации

Это проект следующего этапа, **не утверждённый routing contract**. В первой поставке URL сохраняются. Общую оболочку внедрять после решения о названиях и третьем пункте; одного переименования вкладки недостаточно для новой структуры библиотеки или пары.

| Библиотека | `/development` | `/questionnaires`, `?run={encodedId}`, `?program={encodedKey}#programs` |

При access-lost убрать защищённые данные и устаревшие ссылки на действия. Сам ended не означает отказ в доступе ко всем сохранённым данным: допустимые read-only переходы к профилю, истории и результатам определяются текущим Pair-контрактом. У открытой по ссылке страницы сохраняется выход через `BackBar` с безопасным fallback. Глобальная навигация отделена от редактирования и не сбрасывает несохранённый текст без предупреждения. Не применять key по pathname ко всему дереву или переносить root layout в client component.

## Условия motion-пилота

До установки новой production-зависимости подготовить точный пакет/версию, проверку текущих Next/React/SDK/CSP, client boundary, альтернативу на CSS, сценарий отключения и план измерений; затем получить предусмотренное `AGENTS.md` согласование. Версия здесь намеренно не выбрана. GSAP, полный UI kit и SDK upgrade «на будущее» не нужны.

Если выбран Motion, проверить по документации выбранной версии `MotionConfig reducedMotion="user"`, локальный `useReducedMotion` и целесообразность LazyMotion. Не смешивать обычные импорты с lazy-стратегией; не считать базовый feature bundle поддержкой layout/drag. AnimatePresence допускается у локальных устойчивых границ, без перемонтирования Discord bootstrap.

Стартовые ориентиры из документа 02: press 100–140 мс, шаг формы 160–220 мс, диалог 180–240 мс; окончательные значения определяются после проверки. При reduced-motion исключить scale, большие перемещения и бесконечные декорации. Действие доступно сразу; animation callbacks не определяют успех, награду или раскрытие.

При 401/403/подтверждённой потере доступа приватный узел убирается немедленно, включая скрытые панели, без exit-анимации. В скрытой вкладке/PIP лишние эффекты приостанавливаются по реально доступным механизмам. Сравнение bundle и загрузки выполняется на одном окружении и сценарии; численный бюджет задаётся после baseline, без выдуманных FPS.

## Матрица приёмки и выпуск

| Группа | Обязательные состояния/переходы |
| --- | --- |
| Solo | Новый после входа/onboarding; возвращающийся; нет продолжений; есть занятия/программа; личные функции при наличии пары |
| Приглашение | `EXISTING_PARTNER` без приглашения; ожидание; claim; требуемое подтверждение каждой стороны |

| Надёжность | Loading, empty, network error, retry, auth-required, access-lost, смена пары; поздний ответ не восстанавливает старые данные; refresh-on-return без гонок |
| Продолжения | Deep link run/программы; 30→35 и «Показать ещё»; возврат/перезагрузка; закрытая или недоступная парная запись не всплывает из кэша |
| Формы | Keyboard-only, screen reader, focus/return, сохранение черновика в рамках сценария, предупреждение при уходе, submit/retry/timeout, конфликт revisions |
| Viewport | Ширины 320/360/390/430 px, широкий desktop и короткий landscape (например, 844×390); resize iframe, 200% масштаб, длинный RU, экранная клавиатура и safe areas |
| Motion/host | Оба reduced-motion режима; без эффектов; hide/return; отдельная проверка настоящего Discord desktop/Android/iOS, включая доступные focused/PIP/grid режимы |

Для обзорного экрана — одна основная прокрутка; у модального сценария — одна прокрутка содержимого и заблокированный фон. Отсутствие горизонтального overflow проверять на реальных размерах, а не только через `overflow-x: clip`.

Команды для будущей реализации существуют в [package.json](../package.json); их назначение и guard-условия — в [TESTING.md](TESTING.md). Browser-режим запускать после `npm run build` командой `npm run acceptance:browser -- --mongod <absolute-path>` только по [локальной инструкции](LOCAL_ACCEPTANCE.md). Не применять этот шаблон с невыясненным путём mongod или runtime-настройками основной копии.

По поздним этапам добавлять только затронутые проверки: `selfcheck:mvp-onboarding`/`selfcheck:entry-pairing` для входа, `selfcheck:pair-invite` для приглашений, `selfcheck:matching-ui`/`selfcheck:matching-product`/`selfcheck:matching-disclosure` для знакомства, `selfcheck:weekly-checkin` для check-in, `selfcheck:product-workspace`/`selfcheck:continuation-ui` для занятий и общей жизни. DB-интеграции нужны при изменении orchestration/lifecycle, затрагивающем серверное поведение, а не автоматически для CSS. Для общих UI/routing изменений обязательны build и browser smoke; перед рискованным завершением использовать [CODE_REVIEW.md](CODE_REVIEW.md).

Каждый PR завершается небольшим before/after одного и того же состояния, списком выполненных проверок и пробелов, обновлением профильного активного документа и changelog. Реальный Discord и local synthetic evidence фиксируются раздельно. Откат выполняется отдельно для конкретного UI-изменения; перенос данных или миграция для этих этапов не предусмотрены.
