# Анкеты → личные характеристики → профиль пары: проверка 2026-09-09

**Результат: сквозная продуктовая механика не завершена.** Работоспособность Factor Engine и недельной сводки не подтверждает обновление характеристик после обычной анкеты. Предыдущая приёмка продуктовых маршрутов проверяла навигацию, сохранение и взаимные действия; она не подтверждала эту аналитическую цепочку.

Проверка выполнена на текущем незакоммиченном дереве, с сохранением предыдущей работы. Изменены только средства проверки и документация; runtime, API, схема БД, capture policy и формулы не менялись. Operating mode: `FEATURE_CHANGE` для целевого расширения проверок одного функционального потока.

## Подтверждённые проблемы

| Приоритет | Пользовательский путь | Фактическое поведение | Причина |
| --- | --- | --- | --- |
| P1 | Обычная личная или парная анкета / саморефлексия библиотеки → обновление характеристик | Ответы и завершение сохраняются, но Factor evidence и новые расчёты не создаются. Повтор личной анкеты с другими ответами создаёт отдельную приватную запись без изменения характеристик | `questionnaires.service.ts` записывает `semanticStatus: UNMAPPED`; завершение парной анкеты обновляет session/reward. `development.service.ts` сохраняет completion/progress/reward. Связей вопрос → measurement → factor нет |
| P1 | Открыть профиль и понять свою характеристику | Даже для рассчитанного фактора карточка сообщает лишь доступность, уверенность и свежесть. Две разные характеристики с одинаковыми метаданными имеют одинаковый owner DTO | `factorProfileSummary.service.ts` не выбирает value; `factorProfile.dto.ts` не содержит интерпретации значения, `neutralWording` зависит от доступности |
| P1 | Начальная анкета с ответами «только для расчёта пары» → личный профиль | Данные рассчитаны, но личные карточки остаются «Нет данных» | `onboardingFactorEngine.service.ts` создаёт projectionPurpose PAIR_MODEL/MATCHING; owner summary читает только OWNER_PROFILE. Это текущая граница целей использования, а не потеря записи |
| P1 | Оба разрешили расчёт пары в начальной анкете → связанные характеристики пары | В тестовой паре у обоих есть личные PAIR_MODEL snapshots предпочтения структуры, но чтение сводки и recommendation inputs не создаёт парную оценку этого фактора | Начальные snapshots без contextPairId не включаются в текущий pair runtime: weekly работает по четырём недельным факторам, activity refresh — по ограниченным факторам и evidence с конкретным pairId. У предпочтения структуры определена стратегия для COHABITATION, которую текущий парный экран также не материализует. Нужен явный выбор применимого контекста, а не автоматическое применение стратегии ко всем парам |
| P2 | Недельная отметка → личные характеристики | Недельная парная сводка обновляется, личные карточки не меняются | Weekly evidence/snapshots имеют PAIR_MODEL_ONLY / PAIR_MODEL, а owner summary требует OWNER_PROFILE |

Первый пункт проверен отдельно для трёх механизмов: обычные личные анкеты, парные questionnaire sessions и REFLECTION в библиотеке. Термин «анкета» в интерфейсе сейчас скрывает разные механизмы хранения и разные последствия.

## Что работает

- Начальная анкета с PRIVATE-ответами создаёт три EvidenceEvent и соответствующие snapshots: восстановление разговора, предпочтение структуры, план о детях. В owner profile предпочтение структуры и план о детях становятся AVAILABLE; для навыка один ответ корректно даёт INSUFFICIENT, поскольку правило требует два наблюдения. Двенадцать вопросов не означают двенадцать измеряемых характеристик.
- Повтор завершения той же начальной анкеты не дублирует evidence/snapshots.
- Недельный цикл через реальные доменные методы: первый участник → ожидание без общих сигналов; второй → ENOUGH и четыре качественных сигнала. Повтор отправки не создаёт новые evidence. Сырые значения и provenance в парный DTO не попадают.
- `factor-engine-runtime.integration.ts` подтверждает новые ревизии после новых данных, пересчёт свежести, детерминированный повтор, отсечение некорректных источников и разделение разных контекстов пары.
- Сохранение обычных анкет и саморефлексии действительно работает. Отсутствие изменения характеристик воспроизводится после успешного сохранения.

## Браузерное воспроизведение

Production-сборка текущего приложения; `acceptance:browser --scenario existing-partner`, две синтетические учётные записи. Для этого сценария начальная анкета подготовлена с обязательными ответами PAIR_MODEL_ONLY и пропуском необязательных вопросов.

1. В `/profile` показаны 12 карточек: 11 «Нет данных», план о детях «Не определён».
2. Из профиля открыт каталог и саморефлексия «Как я веду разговор».
3. Через UI выбраны ответы на три вопроса и впечатление; нажата кнопка сохранения.
4. Появились «Личное занятие завершено» и «Ваш результат сохранён» с собственными ответами.
5. Возврат в профиль и полноценная перезагрузка: те же 11 «Нет данных» и одна «Не определён». Навык восстановления разговора не изменился.

Эта проверка не использует реальные пользовательские данные и не подтверждает Discord OAuth/iframe. Browser harness штатно остановлен через собственный POST /stop.

## Воспроизводимая проверка

```powershell
npm run acceptance:local -- --mongod 'C:\path\to\mongod.exe' --suite factors --mongo-port 27045
```

Используется существующий изолированный harness: собственный MongoDB replica set, новый каталог и отдельная `_test` БД для каждого набора, без чтения `.env` и production credentials. Произвольное имя скрипта передать нельзя; `--suite` ограничен `product` и `factors`, доступен только integration mode.

Набор `factors` запускает:

1. `onboarding-factor-engine.integration.ts` — создаёт настоящего синтетического пользователя для текущего пути награды; проверяет материализацию, цели использования и повтор. Исправлена устаревшая тестовая предпосылка: раньше пользователя не создавали, а действующий economy service требует существующий аккаунт.
2. `factor-engine-runtime.integration.ts` — расчёт, свежесть, повтор и контекст пары.
3. `factor-profile-flow.integration.ts` — новые проверки всей цепочки через реальные сервисы/БД/owner DTO, включая подтверждение пяти разрывов выше.

**PASS аудита означает, что описанное поведение воспроизведено, включая отсутствие требуемой функции. Это не release gate готовности механики.** Финальная строка отдельно выводит `questionnaireProfileWorkflowReady: false` и `confirmedProductGaps: 5`. При реализации механики соответствующие проверки отсутствия поведения надо заменить проверками целевого результата; нельзя сохранять их как желательное продуктовое поведение.

Последний содержательный прогон всех трёх наборов: PASS, штатный `cleaned-up`. Также выполнены typecheck, targeted lint, local-acceptance/user-profile-summary selfchecks и changed-file agent checks. Сборка приложения заново не нужна: в runtime этой задачей ничего не менялось; браузер проверял последнюю production-сборку предыдущего этапа.

## Что нужно реализовать для ожидаемой механики

1. Утвердить измеряемые характеристики и связь конкретных вопросов/вариантов с ними. Сейчас опубликованные материалы библиотеки помечены DEMO_SELF_REFLECTION, а текущие продуктовые решения прямо отделяют их от измерений. Простое суммирование ответов по шести разделам не является существующей моделью.
2. Разделить видимость собственного результата и разрешение использовать его в паре. Собственный профиль должен понятно объяснять рассчитанную характеристику; для парной проекции необходимо сохранить явные разрешения и ограничения контекста.
3. Подключить версии анкет к существующему evidence pipeline: валидация, идемпотентный источник, новая версия собственного расчёта, повторное прохождение, обработка незавершённой материализации.
4. Пересчитывать разрешённые парные характеристики после изменения личных данных любого участника, сохраняя значения/версии исходных snapshots и выдавая только согласованную качественную интерпретацию пары.
5. Проверять цепочку по изменению конкретных значений/интерпретаций и парного результата, включая противоположные ответы, пропуск, отзыв разрешения, повтор, смену пары и reload. Зелёные тесты сохранения/навигации недостаточны.

Основания действующих ограничений: `docs/PRODUCT_DECISIONS.md` (пункты 6–7 и правило об отсутствии evidence из невалидированного контента), `docs/PRODUCT_WORKSPACE_UPDATE.md`, `docs/ARCHITECTURE.md`, `docs/TARGET_DOMAIN_MODEL.md`. Исправление продуктового разрыва требует согласования интерпретаций и контракта профиля; этот аудит не подменяет их произвольными формулами.
