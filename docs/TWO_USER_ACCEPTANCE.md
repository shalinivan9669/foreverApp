# Приёмка «Вместе» двумя участниками

Дата подготовки: 2026-09-05. Это проверка текущего этапа продолжения, отдельно от исторических результатов в [PRODUCT_IMPLEMENTATION.md](PRODUCT_IMPLEMENTATION.md). Продуктовые правила: [вход](ENTRY_AND_PAIRING_UPDATE.md), [знакомства](MATCHING_PRODUCT_UPDATE.md), [библиотека и общая жизнь](PRODUCT_WORKSPACE_UPDATE.md).

## Воспроизводимый локальный запуск

Для автономного запуска с новым собственным экземпляром MongoDB используйте [локальную приёмку](LOCAL_ACCEPTANCE.md): `npm run acceptance:local -- --mongod <абсолютный-путь>`. Она также предлагает browser-режим с двумя синтетическими сессиями после `npm run build`. Описанный ниже прежний aggregate по-прежнему подходит для уже подготовленного отдельного replica set.

Установленные зависимости проекта и отдельная локальная MongoDB replica set обязательны. Команда не читает `.env` и не использует обычный `MONGODB_URI` как запасной вариант.

```powershell
$env:MATCHING_TEST_MONGODB_URI = 'mongodb://127.0.0.1:27018/vmeste_acceptance_test?replicaSet=vmesteContinuation&directConnection=true'
npm run integration:two-user-acceptance
```

Имя replica set и порт должны соответствовать самостоятельно запущенному **тестовому** экземпляру. URI выше описывает временный экземпляр текущей проверки; команда сама MongoDB не запускает. Допускаются только `mongodb:`, loopback `127.0.0.1`/`localhost`, указанный replica set и имя с окончанием `_test`. Без command-scoped URI команда завершается до запуска дочерних сценариев. Внешний hostname отклоняется до соединения.

Runner создаёт новое имя `_test` для каждого из шести наборов и каждого запуска, используя переданное имя лишь как префикс. Он запускает существующие сценарии последовательно, выводит имя набора, тестовой базы, статус, длительность и безопасные диагностические этапы, останавливается при первой ошибке. Каждый набор удаляет собственные синтетические записи по уникальным идентификаторам; `dropDatabase` и очистка пользовательских коллекций не используются. Для диагностики можно запустить указанный ниже отдельный набор с явным локальным `MONGODB_URI`; matching-наборы требуют `MATCHING_TEST_MONGODB_URI`.

В `two-user-mvp` три последовательные недели теперь отсчитываются от будущего понедельника UTC, выбранного до включения mock `Date`: часы MongoDB остаются настоящими, поэтому фиксированные даты в прошлом позволяли TTL-monitor удалять короткоживущие audit fixtures во время медленного запуска. Длительности измеряются монотонным `performance.now()`. Aggregate дополнительно пропускает только проверенные имена этапов, тип ошибки и виды оставшихся ресурсов Node.js; полные сообщения дочерних процессов, идентификаторы и payloads не пересылаются. При ошибке тест после `finally` с очисткой и отключением БД завершает процесс с кодом 1, чтобы оставшиеся handles не скрывали результат. Новый полный `acceptance:local` после этих изменений прошёл все шесть наборов, включая 65-run pagination, завершился с кодом 0 и остановил собственную MongoDB на порту 27039.

Native route-handler проверки используют существующие auth guards и подписи sessions только собственных тестовых субъектов. Они не запускают тестовые HTTP endpoints или обход авторизации в приложении и не заменяют браузер/iframe. Отдельный новый browser-harness находится только в `scripts/`: его loopback bootstrap выдаёт сессии ровно двух созданных им fixtures; production API авторизации не меняется.

`integration:economy` и `integration:pair-event-settings` сохраняют исторический строгий guard: только новый локальный экземпляр `127.0.0.1:27029/vmeste_economy_product_test?replicaSet=vmesteTest`. Они намеренно не входят в aggregate с динамическими именами. Дополнительный запуск допустим на отдельно подготовленном тестовом экземпляре с этим точным адресом; guard не ослабляется. Награды за совместную практику уже проверяются в основном workspace-наборе.

Браузерные результаты текущей итерации:

- Различные имена/публичные коды двух fixtures; приглашение по коду → подтверждение получателя → ожидание без Pair → подтверждение владельца → обновление получателя показывает созданную Pair.
- `/development`: 30 → «Показать ещё» → 35, затем «Обновить список» возвращает первую страницу из 30. Самое старое прохождение со второй страницы открывается и восстанавливается по той же прямой ссылке после перезагрузки.
- «Пять минут слушания»: А сохраняет → частичный итог; Б видит необходимость своего результата без заметки А → Б сохраняет → общий итог; обновление и перезагрузка А показывают завершение. В каждом интерфейсе найдена только собственная тестовая заметка, чужая отсутствует.
- Общая задача с 15 минутами: обе формы открыты одновременно → Б сохраняет 25 → старая правка А получает конфликт. Обновление сохраняет черновик А и блокирует сохранение до сравнения. После явного сравнения сохраняются название А и 25 минут Б; обе сессии после перезагрузки показывают одинаковый итог.
- Несохранённый личный черновик после reload пуст, а само прохождение остаётся доступным. Проверка не заявляет отдельного аудита хранилищ браузера; запрет сохранения таких ответов в localStorage остаётся контрактом приложения.
- Для обоих серверов отдельные HTTP-пробы подтвердили: настоящая synthetic session + свой Origin + некорректное тело → 400; чужой Origin → 403; без session → 401; неподходящий Host → 421. Эти пробы не создавали приглашений.

При подготовке обнаружена особенность установленного Next.js: одиночный `next start --hostname 127.0.0.1` формирует серверный URL с нормализованным hostname и отклоняет Origin другого локального адреса. Harness использует два документированных custom-server процесса с точными hostname/port, сохраняя исходные Origin и guards. Один ранний старт превысил таймаут; теперь есть ограниченная диагностика готовности. Причина каждого прежнего зависания полностью не восстановлена; свежий серверный и браузерный проходы успешны.

## Порядок проверки в Discord

Нужны два независимых взрослых тестовых аккаунта A и B в двух отдельных Discord-сессиях и доступная версия Activity с этими изменениями. Убедитесь, что в каждой сессии показаны разные имя и личный код. Для двух путей создания Pair нужны независимые начальные состояния без активной пары; не очищайте неизвестную БД и не используйте личные аккаунты для разрушительного сброса ради повторения.

1. **SOLO и продолжение.** A и B выбирают «Сейчас я без пары», указывают взрослый возраст/город и завершают 12 вопросов. После завершения видны личное развитие и отдельный переход к настройке поиска. Перезагрузите страницу: вопросы не начались заново, первая монета не начислилась второй раз. Начните личную практику или программу, вернитесь на главную и найдите незавершённое занятие. Возобновляется существующий run; несохранённые личные ответы/заметки не обязаны переживать перезагрузку и не должны появляться в localStorage.

2. **Интерес → знакомство → Pair.** Оба публикуют карточку поиска; A открывает B, оставляет реакции на девять пунктов и отвечает на три вопроса. У B есть понятный переход к входящему интересу и ответу. До ответа это pending, Pair нет. B отвечает и принимает; Connection доступен обоим без третьего подтверждения интереса A. Откройте одну тему: сначала отправляет A, B видит факт ожидания, но не ответ. После согласия и ответа B оба обновляют тему и видят разрешённое раскрытие. A предлагает создать пару; до подтверждения B пара не создана. B подтверждает, A обновляет состояние и видит общую Pair. Другие знакомства закрыты, поиск прекращён.

3. **Приглашение существующего партнёра — отдельный начальный сценарий.** A выбирает «У меня уже есть партнёр», завершает настройку и создаёт приглашение. B открывает ссылку до входа, входит своим аккаунтом, проходит entry/onboarding и возвращается к тому же приглашению; проверьте также перезагрузку на промежуточном шаге. Альтернатива — ввод публичного кода A на экране приглашения. Код не авторизует пользователя. B сверяет имя/код A и нажимает «Да, это мой партнёр»: видно ожидание, общей Pair ещё нет. A нажимает «Обновить», сверяет имя/код B и подтверждает его. B нажимает «Проверить подтверждение»; оба видят одну Pair. Повторное нажатие или перезагрузка не создают вторую пару.

4. **Совместная практика.** В активной Pair оба открывают одно совместное занятие. A сохраняет результат с отличимой тестовой личной заметкой: у A частичный итог и ожидание B, у B доступно собственное завершение. Запишите баланс обоих. B завершает со своей другой тестовой заметкой; A нажимает «Обновить общий итог» либо возвращается на экран и видит завершение и следующий шаг. Награда появляется каждому один раз; повторное сохранение/обновление её не меняет. В UI и ответах API каждый видит только собственную заметку и собственные ответы, а не заметку другого.

5. **Общая запись и конфликт.** A создаёт задачу, B открывает её. Оба оставляют форму редактирования открытой. B меняет, например, время выполнения 15 → 25 минут и сохраняет. A со старой формой меняет название и сохраняет: должен увидеть конфликт, чужая правка не пропадает. A нажимает «Обновить общие записи», сверяет новые данные и повторяет свою правку; в итоге сохранены новое название и 25 минут. Перезагрузка обеих сессий показывает одинаковую запись.

6. **Повтор и ограниченный доступ.** На тестовом устройстве отключите сеть перед отправкой, дождитесь сообщения об ошибке, восстановите сеть и повторите. Для потери ответа после сохранения проверьте обновление/повтор без дубликата интереса, результата, награды или записи. В отдельном незавершённом знакомстве проверьте pause/resume; пауза занимает место среди трёх и не разрешает отправлять новые ответы. Для paused Pair общие записи доступны для чтения, их изменение и завершение совместного занятия закрыты. После завершения связи или блокировки повторите старую ссылку/запрос: приватный ответ или сохранённый mutation receipt не должны обходить действующий запрет. Закрытый экран сообщает состояние и даёт допустимый следующий переход.

Сохраняйте для отчёта только шаг, ожидаемый/фактический результат, версию сборки и окружение. Не присылайте cookies, session JWT, OAuth-коды, приглашения с token, личные ответы или чужие заметки. Отдельно фиксируйте «не проверено», если iframe, сеть или вторая сессия недоступны.

После текущей локальной приёмки слушателей на портах 27039, 27040, 3106, 3107 и 3108 не осталось. Последний browser run завершился exit 0 и `cleaned-up`. Один каталог прерванного раннего запуска (`C:\Users\Admin\AppData\Local\Temp\vmeste-local-acceptance-aYiMK9`) остался: автоматическая проверка разрешений отклонила его удаление с `blocked by policy`; повторных попыток обхода не было. Его процессы остановлены. Следующий обычный запуск сам создаёт новый отдельный replica set и не удаляет старые каталоги.
