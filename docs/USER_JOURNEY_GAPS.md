## Следующий этап — предложение для согласования

Подготовлено 2026-09-09 по вопросу владельца о продолжении. Это проект дальнейших изменений, а не утверждённое поведение и не отчёт об их реализации. Текущий этап — `DOCS_ONLY`; код предыдущих исправлений сохранён. Для F04/F08 дополнительных продуктовых правил не требуется: предлагается совместимое расширение чтения с прежними ограничениями доступа. По [AGENTS.md](../AGENTS.md#L70) изменение публичного API и выбор нового продуктового поведения требуют отдельного согласования.

### F04: собственный список блокировок

- Добавить `GET /api/match/block?limit=20&cursor=...`: только активные блокировки, созданные автором сессии. Предлагаемый DTO списка: `{ items: [{ blockedUserId, username, avatar }], nextCursor }` в обычном API envelope. По умолчанию 20 записей, максимум 100; стабильная сортировка по `blockedId` использует существующий индекс. Параметр владельца от клиента не принимается; курсор не даёт дополнительных прав.
- В профиле и прежних знакомствах открыть список «Заблокированные» с постраничной загрузкой. Удалённый или отсутствующий аккаунт отображается нейтрально, сохраняя возможность снять собственную блокировку.
- Кнопка вызывает существующий `DELETE /api/match/block/{blockedUserId}`. Снимается только собственная блокировка; прежние интересы, знакомства и разрешения показа карточек не восстанавливаются. Встречная блокировка не раскрывается. Появление человека в поиске не гарантируется.
- Модель, миграция и новые зависимости не нужны. Privacy export уже содержит ограниченную выборку блокировок, но его лимит 100 вместе со снятыми блокировками и отсутствие пагинации не позволяют использовать его как полноценный список.
- Проверки реализации: изоляция двух владельцев и встречных блокировок; идемпотентный DELETE без восстановления старых связей; несколько страниц, удалённый аккаунт и снятие блокировки в другом окне.

Основания: [MatchingBlock](../src/models/MatchingBlock.ts), [существующая разблокировка](../src/domain/services/matching/social/matchingSocial.service.ts), [privacy export](../src/domain/services/privacyExport.service.ts).

### F08: полный архив доступных завершённых занятий

- Расширить существующий `GET /api/development/runs` необязательным `status=completed`. Без параметра остаются нынешний список незавершённых и его курсоры. Ответ сохраняет `DevelopmentRunPageDTO`: `{ runs, nextCursor }`, до 30 записей.
- Завершённые сортируются по `completedAt DESC, _id DESC`; для старой записи без времени завершения используется `createdAt` только как ключ сортировки, без записи выдуманной даты в БД. Курсор завершённых имеет отдельную версию/метку; его нельзя применять к незавершённым.
- Каждая страница проверяет автора сессии, его участие и завершение, действующий доступ к личному/совместному результату и контенту. Прежние ended пары не открываются. Ограничения применяются до лимита. Изменение области доступа между страницами использует существующий `RUN_LIST_CHANGED` и перезагрузку первой страницы.
- Архив загружается по запросу со страницы библиотеки. Старый результат открывается существующим `?run=<id>`, без нового прохождения или награды. Ошибка/повтор/обновление архива не сбрасывают открытый результат и несохранённый ввод. Ответы и заметки не добавляются в DTO списка.
- Новая модель и миграция не нужны. Сортировка полного архива может потребовать отдельного индекса при росте данных; изменение индексов не входит в это предложение.
- Проверки реализации: 65 результатов страницами 30/30/5, одинаковые даты и отсутствие `completedAt`; совместимость прежних запросов/курсоров; отрицательные проверки доступа и смены пары; гонки загрузки/обновления; открытие старого результата без `POST /start`.

Основания: [runs route](../src/app/api/development/runs/route.ts), [development service](../src/domain/services/development.service.ts), [страница библиотеки](../src/features/development/DevelopmentPage.tsx).

### F01: решение о смысле личного состояния

Нужно согласовать, что показывает собственный профиль, когда старый личный тест и свежие собственные наблюдения в текущей паре дают разные результаты. Например: две недели назад человек указал высокую нагрузку, на этой неделе — низкую.

| Вариант | Видимый результат | Изменение |
| --- | --- | --- |
| Раздельный показ | «По личной анкете» и «В текущей паре» со своими датами, актуальностью и историей. Истёкший источник не выдаётся за актуальное состояние. | Рекомендуемый вариант для сохранения существующих правил вычисления: разделить контексты в UI/DTO; новые карточки требуют устойчивой идентификации, одного `factorKey` уже недостаточно. |
| Единый обновляемый ориентир | Собственные новые наблюдения уточняют один результат по правилам конкретного фактора; для временного состояния учитывается свежесть. | Нужно отдельное явное правило собственной проекции, сохранение происхождения и устранение повторного учёта одного ответа. Нельзя просто усреднить два готовых результата или убрать фильтр пары. |
| Приоритет текущей пары с запасным личным результатом | Пригодные данные нынешней пары показываются первыми; иначе — ещё актуальные личные. Если пригодных данных нет, показывается отсутствие актуального результата. | Форма DTO может сохраниться, но часть допустимых личных наблюдений перестаёт влиять при появлении парного результата. |

Во всех вариантах закрытые ответы анкеты остаются неизменными, чужие ответы и контекст бывшей пары не попадают в собственный текущий результат. Matching и общий профиль пары сохраняют отдельные правила источников и разрешений. Изменение F01 не отменяет исправление F02: общий результат пары «Нагрузка по личным анкетам» и «Состояние недели» сейчас являются разными представлениями.

Основания: [выбор собственных snapshots](../src/domain/services/factorProfileSummary.service.ts), [изоляция контекстов расчёта](../src/domain/model/snapshots/snapshots.ts), [одно значение и история в текущем DTO](../src/lib/dto/factorProfile.dto.ts).

После согласования F04/F08 реализуются в режиме `API_CONTRACT_CHANGE` с обновлением действующих контрактов и целевыми проверками. F01 начинается после выбора смысла результата; конкретная классификация и границы реализации определяются выбранным вариантом. Новые зависимости, миграции, удаление аккаунта и отложенные продуктовые функции в следующий этап не включены.

## Явно отложенное

- Telegram/mobile и другие провайдеры входа; сейчас реализован Discord.
- Валидированные методики и администрирование пакетов, аналитика повторяющихся конфликтов, родительство.
- Новый сценарий расставания, сопровождение и архив старой пары; банковские интеграции, фотохранилище, внешнее бронирование. Реальные платежи и собственный мессенджер не входят в согласованный объём.
- Повтор одноразовых тестов за монеты. Новые измерительные тесты сейчас не начисляют монеты — это явно записано в [контракте](FACTOR_MEASUREMENT_CONTRACT.md).
- Восстановление удаления аккаунта после сбоя. Дефект остаётся: [beginDeletion](../src/domain/services/accountDeletion.service.ts#L548) оставляет аккаунт DELETING, [ошибка](../src/domain/services/accountDeletion.service.ts#L588) переводит запрос в FAILED, но после reload [настройки](../src/app/profile/(tabs)/settings/page.tsx#L22) и [чтение статуса](../src/app/api/privacy/deletion-request/route.ts#L24) требуют обычную активную сессию. Специальный [execute](../src/app/api/privacy/deletion-request/execute/route.ts#L14) допускает retry, однако стандартный UI до него не доходит. Владелец явно отложил эту работу; повторно не назначаем её ближайшей без изменения решения.

Источники решений: [PRODUCT_DECISIONS](PRODUCT_DECISIONS.md), [PRODUCT_IMPLEMENTATION: ограничения](PRODUCT_IMPLEMENTATION.md#L73), [историческое доказательство recovery](audits/2026-09-05-auth-privacy.md).
